## 1. 背景与痛点

典型使用方式：从服务器上下载日志文件，直接用本扩展打开排查——日志是独立文件，不在任何项目工作区内。这类排查几乎总是走同一条固定流程：

1. 拿到线索：一个报错关键词（如 `支付回调失败`）+ 一个业务唯一参数（订单号 / userId / traceId）
2. 在搜索框输入「关键词 + 业务参数」（多关键词 AND），定位到问题附近的日志行
3. 从命中行提取线程名（如 `http-nio-8080-exec-12`），手动筛选该线程
4. 在命中行附近上下翻找，阅读这条请求的完整日志链路，找到根因

当前扩展（v1.2.9）每个环节都已单独支持：多关键词 AND 搜索、点击线程名筛选、书签、注释、跳转、导出等。但流程是**手工串联**的：

- 同类问题（如「支付回调失败」）每次排查都要重新输入一遍相同的关键词组合；
- 搜索、筛线程、打书签、跳转要一步步手动点，步骤多、易打断思路；
- 常用的排查套路没有保存和复用的机制。

**而且排查套路并不总是同一条链。** 有时是「搜索 → 筛线程 → 看上下文」；有时是「关键词 A 查一遍全部打书签 → 关键词 B 查一遍全部打书签 → 打开书签管理逐一排查」。因此模板不应该是写死的单链路，而应该是**可自由编排的动作序列**。

## 2. 目标与非目标

### 目标

1. 把扩展的现有能力（查询日志、筛选、书签、注释、跳转、裁剪等）抽象为可配置的**动作**；
2. **排查模板 = 参数 + 线性动作序列**：运行时顺序执行，动作之间传递上下文（命中集、提取到的线程名等），流程完全由用户编排，不写死；
3. 模板**手动配置**，提供两种配置形式：**可视化编辑**（默认）与 **JSON 文本编辑**（高级），二者是同一份数据的两个视图；
4. 支持**模板共享**：导出为 JSON（剪贴板 / 文件）发给同事，对方一键导入；
5. 交互收敛为「打开面板 → 选模板并运行 → 填参数 → 开始执行」。

### 非目标（本期不做）

- 不做条件分支、循环、并行步骤——模板是**线性步骤序列**，这是刻意简化，保证引擎和心智模型都简单；
- 不做跨文件/多文件联合排查（每个面板模板独立）；
- 本期不做日志自动归因、异常聚类等智能化能力（列入后续计划，见第 6 节 P2）；
- 不做共享服务端 / 云同步，也不做依赖工作区的共享（排查对象是独立日志文件，常不在任何工作区内；共享统一走 JSON 导入/导出，见目标 4）；
- MVP 不支持模板内正则关键词（规避 ReDoS 风险面，见第 8 节）。

## 3. 用户场景

**场景 A（固定定位链）：**

> 支付组的小王每周都会遇到「回调失败」类工单。以前：打开日志 → 输入「支付回调失败 订单号 xxx」→ 搜索 → 右键命中行筛线程 → 翻页找上下文，共 5 步以上。
> 现在：点「排查模板」→ 选「支付回调失败排查」→ 填入本次订单号 → 运行。动作序列：查询 → 从命中提取线程并筛选 → 跳转到命中行，日志视图直接呈现筛选后的结果，光标停在命中行上。

**场景 B（多查询批量书签）：**

> 同一个订单号，小李想先把所有可疑点标出来再统一排查。模板动作序列：查询「支付回调失败 + ${orderNo}」→ 对全部命中打书签「回调失败」→ 查询「订单超时 + ${orderNo}」→ 对全部命中打书签「订单超时」。运行结束后打开书签管理，两组书签都在，逐条跳转分析。

**场景 C（临时排查，无模板）：**

> 排查一个从未见过的问题，已经手动搜到一条可疑日志。右键该行选「从此行开始排查」→ 自动提取线程名、筛选该线程并跳转（P1）。

**场景 D（线程名不可靠的兜底）：**

> Web 容器线程名（`http-nio-exec-N`）是池化复用的，单靠线程筛选可能混入其他请求的日志。筛选动作可叠加「时间窗口」：只显示命中时间 ±N 秒内的该线程日志（P1）。

## 4. 方案对比

| 方案 | 思路 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 动作流水线模板 | 把所有现有能力抽象成动作，模板 = 参数 + 线性动作序列，运行时顺序执行并传递上下文 | 表达力覆盖各种排查套路（含固定链与多查询书签）；动作即现有功能，实现是「编排」而非「新造」；后续加动作成本低 | 需要一个小型执行引擎和步骤编辑器 | ✅ 采用 |
| B. 固定定位链模板（v1 方案） | 模板只有 keywords / params / autoThreadFilter 等固定字段 | 实现最小 | 表达力锁死在一条链上，无法表达「多查询 + 批量书签」类流程，与真实排查模式不符 | ❌ 已被 A 取代 |
| C. 独立排查向导面板 | 新建侧边 Webview 分步引导 | 空间大 | 割裂感强（排查仍要在主视图做）；实现量大 | ❌ 放弃 |

## 5. 详细设计

### 5.1 核心概念：动作流水线（执行引擎）

模板运行 = 按顺序执行动作序列。引擎维护一个**执行上下文**，动作读它、也写它：

```
context = {
  params,      // 本次运行填入的参数值
  hits,        // 最近一次「查询」动作的命中集（行对象数组）
  lastHit,     // 用户从命中列表中选中的那条（hitPolicy=ask 时）
  lastThread   // 最近一次从命中行提取到的线程名
}
```

**MVP 动作集（4 种，全部复用现有能力；跳转动作已移除，见决策 13）：**

| 动作 | 行为 | 产出 / 副作用 | 复用的现有能力 |
|---|---|---|---|
| 查询日志 `search` | 按关键词列表做 AND 搜索，关键词支持 `${param}` 占位；可勾选 `afterLastHit`（从上一步命中行之后开始查）与 `sameThread`（仅同线程日志），实现链式时序定位 | 更新 `context.hits`，并按 hitPolicy 决定交互；搜索重新定义查询上下文（替换关键词、清空其余过滤器，sameThread 时以线程筛选呈现）；选中单条后自动定位到该行 | 现有多关键词 AND 搜索匹配 |
| 筛选 `filter` | 按线程/类名/方法/级别/时间范围过滤；值可为字面量、`${param}`，或 `lastHit`（从命中行自动提取线程名） | 更新 `unifiedFilters`，写入 `context.lastThread`；筛选后自动定位到命中行 | `setFilterAndApply()`、`extractLogFields()` |
| 书签 `bookmark` | 对「全部命中」或「当前视图」批量打书签，名称支持 `${param}`（默认「行 N」） | 写入 bookmarks 集合并刷新书签 UI | 现有书签功能 |
| 注释 `comment` | 对「全部命中」或「当前视图」批量添加注释，内容支持 `${param}` | 写入 comments 集合并刷新注释 UI | 现有注释功能 |

P1 动作：高亮规则、导出结果、取消筛选（清空 unifiedFilters）、折叠开关。动作类型用白名单枚举，不在白名单内的步骤直接校验失败。

**查询动作的两个策略字段（流水线的交互点）：**

- `hitPolicy` — 命中 N 条时怎么办：
  - `ask`（默认）：**弹出命中列表由用户点选一条**，写入 `context.lastHit`（延续已确认的决策：多命中必须弹列表）；
  - `all`：不打断，全部命中作为结果留给后续动作（批量书签场景专用）；
  - `first`：不打断，自动取第一条（留给明确想自动化的模板作者）。
- `onEmpty` — 命中 0 条时怎么办：
  - `stop`（默认）：提示「未找到」，终止流水线并保留参数表单供修改；
  - `skip`：警告后继续执行下一步（多查询书签场景：某组关键词没命中不该中断整体流程）。

**运行过程反馈**：执行中显示步骤进度（「步骤 2/5：正在打书签…」）和「停止」按钮；每个动作之间让出一帧 UI，长流水线不会卡界面。结束后显示**执行摘要**（打了几个书签、筛选的线程名、跳转行号），并附「取消筛选」快捷操作。

**执行示例——场景 B 的动作序列：**

```json
[
  { "type": "search",   "keywords": ["支付回调失败", "${orderNo}"], "hitPolicy": "all", "onEmpty": "skip" },
  { "type": "bookmark", "target": "hits", "name": "回调失败-${orderNo}" },
  { "type": "search",   "keywords": ["订单超时", "${orderNo}"],     "hitPolicy": "all", "onEmpty": "skip" },
  { "type": "bookmark", "target": "hits", "name": "订单超时-${orderNo}" }
]
```

**执行示例——场景 A 的动作序列（即 v1 的固定定位链，只是现在用动作表达；筛选后自动定位到命中行，无需显式跳转步骤）：**

```json
[
  { "type": "search",  "keywords": ["支付回调失败", "${orderNo}"], "hitPolicy": "ask" },
  { "type": "filter",  "field": "threadName", "value": "lastHit", "keepKeyword": true }
]
```

**降级路径**：`filter` 的 `value: "lastHit"` 提取不到线程名时不失败——跳过该动作，记入执行摘要（「该行未识别到线程名，已跳过筛选」），流水线继续。

### 5.2 模板数据结构

```js
{
  id: 'tpl_1725072000000',          // 'tpl_' + 创建时间戳
  schemaVersion: 1,
  name: '支付问题综合排查',          // 必填，列表展示
  description: '两条查询批量打书签',  // 选填
  params: [                          // 运行时输入，供所有动作通过 ${key} 引用
    { key: 'orderNo', label: '业务单号' }
  ],
  steps: [ /* 动作数组，顺序即执行顺序 */ ],
  createdAt: 1725072000000,
  updatedAt: 1725072000000
}
```

- `steps` 是线性数组，**无嵌套、无分支、无循环**——结构上的强制简化；
- 每个动作对象按 `type` 走字段白名单校验，未知字段丢弃；
- 占位符语法统一为 `${key}`，只允许引用 `params` 中声明的参数；关键词本体不解析占位符以外的内容；
- v1 讨论稿中的固定结构（keywords / autoThreadFilter 等顶层字段）**废弃**——从未发布，无兼容负担；
- **持久化位置**：webview `localStorage`（key：`investigationTemplates`），与现有 `customHighlightRules` 同一先例。模板是**用户级资产而非工作区资产**：排查对象多是从服务器下载后直接打开的独立日志，模板必须跟着人走，同一台机器上跨窗口/文件夹可用；跨机器迁移与分享统一走导入/导出。

### 5.3 配置形式：可视化 + 纯文字（同一数据的两个视图）

**可视化编辑器（默认视图）：**

```
┌─ 编辑模板 ─────────────────────────────────────────────┐
│  名称：[支付问题综合排查 ]   描述：[两条查询批量打书签 ]   │
│  运行参数：[+ 添加参数]  →  业务单号(orderNo) [×]         │
│ ┌──────────────────────────────────────────────────┐ │
│ │ 1 ▾ 查询日志   关键词: 支付回调失败, ${orderNo}     │ │
│ │              命中策略: 全部保留  空结果: 跳过   [×] │ │
│ │ 2 ▾ 打书签     对象: 全部命中  名称: 回调失败-...  [×]│ │
│ │ 3 ▾ 查询日志   关键词: 订单超时, ${orderNo}         │ │
│ │ 4 ▾ 打书签     对象: 全部命中  名称: 订单超时-...  [×]│ │
│ └──────────────────────────────────────────────────┘ │
│  [+ 添加动作 ▾：查询/筛选/书签/跳转]   [↑] [↓] 调序     │
│   [JSON 模式]              [取消]  [保存模板]           │
└────────────────────────────────────────────────────────┘
```

- 「添加动作」下拉选择动作类型，每种动作渲染对应的属性表单（字段与 5.1/5.2 的 schema 一一对应）；
- 步骤支持上移/下移/删除；
- **「JSON 模式」页签**：直接以 JSON 文本查看/编辑步骤序列，带格式校验（校验失败不允许保存并标出错误位置）。适合高级用户快速改配置、排错，也和导入/导出的格式完全一致——**可视化与纯文字是同一份数据的两个视图，随时切换**。

**运行参数表单**（模板有 `params` 时弹出）：

```
┌─ 运行模板：支付问题综合排查 ──────────────┐
│  业务单号：[____________________]          │
│            [取消]   [开始执行]             │
└───────────────────────────────────────────┘
```

**命中选择列表**（查询动作 `hitPolicy=ask` 且命中 N 条时弹出）：

```
┌─ 选择命中（共 37 条）──────────────────────┐
│ ○ 行 10342 · 14:23:01.882                  │
│   ...支付回调失败 orderNo=20260831... 超时  │
│ ● 行 12088 · 14:25:44.103                  │
│   ...支付回调失败 orderNo=20260831... 重试  │
│ ○ 行 15201 · 14:31:02.550                  │
│   ...支付回调失败 orderNo=20260831... 失败  │
│            [终止]   [用这一条继续]          │
└────────────────────────────────────────────┘
```

### 5.4 入口

1. **工具栏「排查模板」按钮**（主入口，位于「高级搜索」旁）：

```
┌─ 排查模板 ────────────────────────────────────────┐
│  [+ 新建模板]          [导入]（剪贴板 / 文件）      │
│ ┌──────────────────────────────────────────────┐ │
│ │ ▶ 支付问题综合排查                            │ │
│ │   2 个参数 · 4 个动作 · 上次运行: 08-31       │ │
│ │                       [运行] [编辑] [⋯]       │ │
│ └──────────────────────────────────────────────┘ │
│  [⋯] 展开：复制模板 / 导出到剪贴板 / 删除          │
└──────────────────────────────────────────────────┘
```

2. **日志行右键菜单「从此行开始排查」**（P1，免模板临时链：提取线程 → 筛选 → 跳转）
3. **命令面板** `日志查看器: 排查模板`（命令 ID `big-log-viewer.showInvestigationTemplates`）

所有弹窗复用现有 modal 风格，样式走 CSS 变量保证 4 套主题兼容。

### 5.5 与现有架构的集成

定位链路（搜索/筛选/书签/跳转）在 webview 内闭环（数据已在内存）；仅「模板共享」需要新增 2 个通用消息 case：

| 能力 | 复用 / 新增 | 位置 |
|---|---|---|
| 多关键词 AND 搜索 | 复用现有搜索匹配逻辑 | `media/webview.js` |
| 线程名提取 | 复用 `extractLogFields()`（与 `LogParser.extractThreadName` 同规则） | `media/webview.js:2792` |
| 筛选 | 复用 `setFilterAndApply({ ... })` | `media/webview.js:3364` |
| 书签 | 复用 bookmarks Map 及书签 UI 刷新 | `media/webview.js:19` |
| 注释 | 复用 comments Map 及注释 UI 刷新 | `media/webview.js:20` |
| 跳转 | 复用现有页内跳转（虚拟滚动） | `media/webview.js` |
| 模板持久化 | 复用 `localStorage` 先例 | `media/webview.js:2151` |
| 状态提示 | 复用 `showFilterStatus()` 状态条 | `media/webview.html` |
| 模板导出为文件 | **新增**消息 `exportTemplates`（宿主端保存对话框 + 写 JSON，实现模式同 `exportLogs`） | `src/logViewerPanel.ts` |
| 从文件导入模板 | **新增**消息 `importTemplates`（宿主端打开文件对话框 + 读文件，内容回传 webview 校验合并） | `src/logViewerPanel.ts` |

剪贴板导出优先在 webview 内用 `navigator.clipboard.writeText` 直写，失败时引导改用「导出为文件」。除上述 2 个共享消息外，**不新增其他 `onDidReceiveMessage` case**。

## 6. 分期实施计划

### P0 — MVP（一个可发布版本）

1. 模板数据结构（params + steps）+ localStorage 读写（含损坏 JSON 容错，坏数据降级为空列表）；
2. 动作流水线引擎：4 种动作（查询/筛选/书签/注释）+ `hitPolicy`/`onEmpty` 策略 + 步骤进度/停止/执行摘要；
3. 模板管理弹窗：列表 / 新建 / 编辑 / 复制 / 删除；
4. 模板编辑器：可视化步骤编辑（增删/排序/属性表单）+ JSON 模式页签（校验后保存）；
5. 模板共享：导出（剪贴板 / `.json` 文件）+ 导入（剪贴板 / 文件），按 id 去重合并、schema 校验；
6. 工具栏「排查模板」按钮 + 命令面板命令（`package.json` 注册 `big-log-viewer.showInvestigationTemplates`）；
7. README、CHANGELOG（`## [Unreleased]`）同步更新（仓库规则要求，同 commit 提交）。

### P1 — 体验增强

1. 更多动作：高亮规则、导出结果、取消筛选、折叠开关；
2. 日志行/搜索结果右键「从此行开始排查」（临时链，免模板）；
3. 筛选动作的时间窗口选项（`timeWindowSeconds`）：解决线程池复用导致的链路污染；
4. 「重新打开命中列表」：不重新执行流水线，从摘要处重选命中继续。

### P2 — 远期可选

1. 模板查询单关键词级「按正则匹配」开关（需明示 ReDoS 注意事项）；
2. 排查会话记录：保存每次运行的参数/命中/书签轨迹，可回放；
3. 模板市场式分享页（纯本地文件聚合展示，不做服务端）；
4. 智能化能力（后续计划，暂不实现）：日志自动归因、异常聚类等——待动作流水线与书签/注释数据积累后探索。

## 7. 验收标准

- 场景 A：选模板 → 填参数 → 运行，最终呈现「线程筛选后的视图 + 光标停在命中行」，交互 ≤ 3 次点击 + 1 次输入；
- 场景 B：两条查询 + 批量书签的模板运行结束后，书签管理中能看到两组命名书签，均可跳转；中途某条查询 0 命中时流程不中断（`onEmpty=skip`）；
- 注释动作：批量注释后在注释管理中可见、可跳转，内容中的 `${param}` 已替换为实际值；
- `hitPolicy=ask` 的查询命中 N 条时必须弹命中列表，用户点选后流水线才继续，且可终止；
- 共享场景：导出的模板（剪贴板 / 文件）在另一环境导入后字段完整还原，重复导入按 id 去重；含未知动作类型/未知字段的 JSON 导入时被校验拦截；
- 可视化编辑器与 JSON 模式切换后数据一致，非法 JSON 不允许保存；
- 模板跨会话保留：关闭面板重开，模板列表不丢；
- 失败路径（0 命中 stop、提取不到线程名、模板 JSON 损坏）均有明确提示且不崩溃；
- 4 套主题下所有新弹窗无样式错乱；
- `npm run lint` 与 `npm run compile` 通过。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 流水线引擎复杂度膨胀 | 动作白名单枚举 + 线性执行（无分支/循环）+ 每个动作一个独立入口函数，逐个手动验证 |
| 线程名池化复用导致链路混入其他请求日志 | P1 时间窗口过滤；状态条明示当前筛选线程名，用户可自行叠加关键词 |
| 模板关键词未来若支持正则，存在 ReDoS 风险 | MVP 明确不支持正则（纯字面量多关键词 AND）；P2 若开放，限定 alternation/嵌套量词并在 UI 提示 |
| 导入他人分享的不可信 JSON | `schemaVersion` + 动作类型/字段白名单校验，未知字段丢弃；单次导入数量与单条大小设上限 |
| 长流水线阻塞 UI | 动作之间让出 UI 帧（异步分片执行），执行中提供「停止」 |
| localStorage 中模板 JSON 被损坏 | 读取时 try/catch + schemaVersion 校验，失败降级为空列表并提示，绝不阻塞打开 |
| localStorage 跨窗口行为与预期不符（模板不互通） | 导入/导出始终可用兜底；必要时把存储迁移到宿主端 `globalState`（新增 `getTemplates`/`saveTemplates` 消息），协议与 UI 不变 |
| webview 剪贴板 API 不可用 | 剪贴板导出失败时提示改用「导出为文件」通道 |
| 与「统一过滤系统」的状态冲突 | 筛选动作走 `setFilterAndApply` 同一条状态通道，可被现有「取消筛选」一键清除，不引入平行状态 |

## 9. 决策记录

**2026-08-31 第一轮评审：**

1. **多命中必须弹出列表由用户选择**，不做「自动选第一条」——在动作模型中落地为查询动作 `hitPolicy` 默认 `ask`；明确作用于全部命中的动作（如批量书签）用 `all`，不打断（该例外是编排模型的需要，见决策 5）。仅 1 条命中时直接采用不打断。
2. **筛线程后默认叠加保留关键词过滤**（筛选动作 `keepKeyword` 默认 `true`），可在模板编辑中按场景修改。
3. **功能定名「排查模板」**：工具栏按钮、弹窗标题、命令标题、README/CHANGELOG 统一用此名称；命令 ID 为 `big-log-viewer.showInvestigationTemplates`。
4. **模板共享只走导入/导出**：P0 提供剪贴板 / 文件两种通道（点对点分享给同事），这也是唯一的共享机制——不做工作区/git 级共享，因为排查对象是从服务器下载的独立日志文件，通常不在任何项目工作区内。

**2026-08-31 第二轮评审：**

5. **模板升级为可编排的动作流水线**：模板 = 参数 + 线性动作序列；动作覆盖扩展现有能力（查询、筛选、书签、注释、跳转、导出、高亮规则等）；流程不固定，支持「多查询批量打书签后汇总排查」这类自由组合。v1 的固定数据结构废弃。
6. **配置形式提供可视化与 JSON 纯文字两种**，二者是同一数据的两个视图；可视化编辑为默认，JSON 模式面向高级用户，且与导入/导出格式一致。
7. **MVP 动作集收敛为 4 种**：查询、筛选、书签、跳转；注释/高亮/导出等动作进 P1。

**2026-08-31 第三轮评审：**

8. **智能化能力（日志自动归因、异常聚类等）列入 P2 后续计划**，本期不做，但保留演进方向——动作流水线与书签/注释数据是其后续的数据基础。

**2026-08-31 第四轮评审：**

9. **注释动作提前至 MVP 动作集**（原 P1）：与书签动作同构（对象 = 全部命中 / 当前视图，内容支持 `${param}`，存储同为行号 Map），实现成本低，随 MVP 一并交付。

**2026-09-02 第五轮评审（开发期反馈）：**

10. **查询动作增加时序约束开关** `afterLastHit`（从上一步命中行之后开始查）与 `sameThread`（仅同线程日志）：链式场景「查第一条 → 书签 → 筛线程 → 找第二条」中，第二条大概率位于第一条之后且大概率同线程，配合 `hitPolicy=first` 即为「上一条日志之后的下一处匹配」。两约束依赖 `context.lastHit`，无法满足时走 `onEmpty` 策略；搜索动作同时把视图过滤器重置为与命中集一致（sameThread 时保留线程筛选，否则清空线程/类名/方法/级别/时间过滤），保证「看到的 = 命中的」。

**2026-09-02 第六轮评审（开发期缺陷修正）：**

11. **命中策略决定查询步骤的产出集**（`context.hits`）：`first` / `ask` 时产出集收敛为选中的一条，后续「打书签 / 加注释」等作用于该条；`all` 时为整批命中，且锚点 `lastHit` 取最后一条，便于继续用 `afterLastHit` 链式推进。修正前的实现里 `first` 只设置了单条锚点而 `hits` 仍保留整批，导致「自动选第一条 + 打书签」把后面所有匹配都打了书签。编辑器中策略与打书签/注释的对象文案同步澄清（「自动选第一条(仅这一条)」「本次查询的命中结果」）。

**2026-09-02 第七轮评审（开发期反馈）：**

12. **筛选/查询单条后自动定位到命中行**：筛选动作执行后视图原来停在筛选结果第一页（即日志开头），现改为存在 `context.lastHit` 时自动 `jumpToLine` 到命中行并高亮；查询动作 `first` / `ask` 选中单条后同样定位（`all` 不定位，便于浏览整批）。显式的「跳转」动作仍保留，用于跳指定行/时间。

**2026-09-02 第八轮评审（开发期反馈）：**

13. **移除「跳转」动作**：可复用模板里写死行号/时间点没有意义（换个日志文件即失效），而「跳到找到的那条」已由查询/筛选动作自动完成（决策 12）。动作类型白名单、执行引擎、编辑器表单中的 jump 全部删除，动作集收敛为查询/筛选/书签/注释 4 种。功能未发布、无兼容负担——含 jump 步骤的存量开发期模板在加载校验时按无效处理，重建即可。

**2026-09-03 第九轮评审（开发期反馈）：**

14. **过滤状态的界面表达与手动操作完全一致**：筛选线程/类名/方法名后，状态条按手动口径显示具体值（「线程名: xxx」等）；筛选日志级别时同步级别勾选框（含全选联动）；关键词回显搜索框、正则勾选归位。不再统一显示「排查模板: 模板名」——具体筛了什么由原有控件表达，模板运行不留专属痕迹。
